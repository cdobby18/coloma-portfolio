Powerlift Pose estimation that holds still long enough to score a lift

A mobile app that reads a lift from video, stabilizes the skeleton, classifies the phase, and scores the rep — on the phone, while the set is happening.

01

The problem

A lifter finishes a set with a video and an opinion. Form feedback usually arrives later, from a coach, if it arrives at all. The gap is not a lack of footage — it is a lack of anything objective to say about it in the moment.

Pose estimation looks like the answer until you try to score with it. Keypoints flicker frame to frame, and a scorer built on raw coordinates produces confident nonsense. Before form means anything, the lift also has to be identified — squat, bench, or deadlift — and split into phases.

Powerlift was built to close that loop on the device: pose, smoothing, features, classification, and a per-rep score, without a cloud round-trip.

The hard part was never finding the joints. It was making them hold still.

02

Constraints

Mobile hardware set the rules. Every constraint below removes a design that would be simpler on a server.

  • On-device inference

    The phone is both sensor and computer. Frames stay on the device; there is no upload path.

  • Real time

    Feedback has to land during or right after the rep, not in a batch job.

  • Noisy input

    Keypoints jitter from frame to frame. Smoothing is part of the pipeline, not a polish step.

  • Phase before score

    Identify the lift and its phase before judging form, or the score has nothing to attach to.

  • Exportable models

    Training happens in Python; inference ships as ONNX or TFLite. An unexportable model is not a result.

03

How it works

Six stages, one of them a filter that exists only because raw keypoints are not trustworthy enough to classify.

I/O AI / ML Process

  1. Capture

    Camera frames stream from the phone. Nothing is uploaded; the frame never leaves the device.

  2. Pose

    YOLOv8 extracts body keypoints per frame. One pass handles both detection and keypoints, which keeps the per-frame budget on mobile realistic.

  3. Stabilize

    A Kalman filter smooths landmark trajectories across frames. It trades a little lag for a lot less jitter — and jitter is what makes a classifier flip.

  4. Features

    Smoothed keypoints become engineered features — angles between joints and how they change over time — instead of raw coordinates fed straight to a model.

  5. Classify

    An SVM labels the lift phase from those features. It is small enough to run beside pose inference, and its decisions can be inspected.

  6. Score

    The per-rep score and a skeleton overlay render in the app, so the output is attached to the frame it describes.

04

Decisions & tradeoffs

Every choice favored latency and size over peak accuracy. That was deliberate for a phone, and it is the cost line in each card.

One pose model, not a stack

YOLOv8 handles detection and keypoints in a single pass, which keeps the pipeline short enough to run per frame.

Tradeoff Less keypoint precision than a heavier multi-stage pipeline. Acceptable when the output is a score band, not a clinical measurement.

Kalman filter over raw landmarks

Smoothed trajectories stop flicker from flipping classifications, and the filter is cheap enough to sit in the frame loop.

Tradeoff Process noise has to be tuned per lift, and smoothing adds a little lag on the fastest reps.

SVM over a sequence model

Small, interpretable, and fast on device — the classifier runs inside the same frame budget as pose.

Tradeoff It only knows the features I engineered. A new lift means new feature work and new labels, not just more data.

On-device over cloud

Frames stay private, the app works offline, and there is no per-inference bill.

Tradeoff Frame rate and thermal limits are set by the weakest phone worth supporting.

Export, don't port

One Python training codebase, exported to ONNX or TFLite for the app.

Tradeoff Conversion gaps: an op can train fine and fail to export. The exported model needs its own check, not just the trained one.

Evaluation gate A model is promoted only after the eval harness clears its FPS and accuracy thresholds. On-device FPS, inference latency, and classification confidence are logged, so a slow or degrading build shows up instead of shipping quietly.
05

Outcome

Powerlift was built as a mobile application and named Overall Best Thesis in 2025. I don't have a published benchmark for it, so I won't quote accuracy or FPS figures without a method behind them.

What exists
  • An end-to-end on-device path: capture → pose → smoothing → features → classification → score
  • YOLOv8 pose estimation with Kalman-smoothed landmarks
  • SVM lift-phase classification from engineered features
  • A mobile interface with a skeleton overlay and per-rep score
  • Overall Best Thesis, 2025
What I can't claim

Accuracy, FPS, or device coverage figures. Those need a held-out set, a named device, and a measurement method. This page won't invent them — the next section is how I'd get them.

06

What I'd change next

  1. Publish the evaluation A labeled set per lift, per-class precision and recall, and the method used to get them. A thesis claim should come with its denominator.
  2. Compare the classifier Run a small temporal model — a 1D CNN or GRU — on the same features and compare it against the SVM on accuracy and on-device latency.
  3. Measure the device floor Log FPS, latency, and thermal state on named phones, then state the hardware the app actually supports.
  4. Calibrate per lifter Thresholds shouldn't be tuned to one body. A short calibration set before the first scored rep would make the output portable.
  5. Close the retraining loop Let corrections in the app become labels, and feed them back into the retraining path the pipeline already has.
