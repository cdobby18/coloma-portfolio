01

The problem

Support work is mostly judgment repeated at volume. Every ticket has to be read, graded for urgency, matched against policy, and answered in a tone that fits the customer. Experienced agents do it in seconds. Everyone else — and everyone on a busy day — does it unevenly.

The obvious automation is to let a model answer. That moves the failure rather than removing it. A fluent reply that isn't grounded in policy is worse than a slow one, because it looks correct.

So the build started from a narrower question: how much of the loop can a model take without taking the decision away from a person?

The answer I implemented: everything up to the send button.

02

Constraints

These were fixed before the first endpoint. Each one removes an easier design.

  • Human authority

    The model drafts, a person sends. There is no autonomous reply path in the product.

  • Grounded or abstain

    Drafts come from the knowledge base and carry citations plus a confidence signal. "No good passage" is an allowed outcome.

  • Fail closed

    If the model call fails, triage falls back to deterministic rules so the ticket still routes.

  • Idempotent intake

    Inbound webhooks are HMAC-verified and deduplicated before a ticket is created.

  • Slow work off the request path

    Notifications and side effects go through a queue instead of blocking the response.

03

How it works

One path from inbound message to a reviewed reply. The dashed node is where the system deliberately stops.

  1. Intake

    Tickets arrive from the app or a signed webhook. Verification and an idempotency check run before anything is written, so a retried delivery never becomes a duplicate ticket.

  2. Guardrails

    Input checks run before the model sees text, and generated drafts are checked again before they reach the queue.

  3. Triage

    An agent labels intent, priority, and sentiment. If the model is unavailable, deterministic rules produce the same three fields so the ticket still lands in a queue.

  4. Retrieve and draft

    Retrieval pulls the closest passages from a FAISS index over the Markdown knowledge base. The model writes a reply grounded in those passages, with citations and a confidence score attached.

  5. Decide

    The draft appears next to the ticket with its sources. A human edits, sends, or escalates — and a risk score routes the sensitive ones to escalation rather than the general queue.

04

Decisions & tradeoffs

Each choice below bought something and cost something. The cost is the part worth reading.

Retrieval over free generation

A draft that cites the passage it came from is auditable, and "nothing relevant found" is a usable answer.

Tradeoff More abstentions than a model that always replies. I'd rather show a gap than ship a confident fabrication.

A deterministic path beside the agent

Triage falls back to rules when the model is down, so routing keeps working.

Tradeoff Rule labels are coarser, and the two paths have to be kept in agreement — a second implementation to test.

Human in the loop, not out of it

Nothing sends itself. The system compresses the read, search, and first-draft steps; the judgment stays with an agent.

Tradeoff It saves drafting time, not headcount — and it puts pressure on review speed. A slow queue defeats the purpose, which is why the board is keyboard-first.

FAISS instead of a managed vector store

The index sits next to the app and rebuilds from Markdown, so there is one less service to run and the source of truth stays readable.

Tradeoff Indexing and re-indexing are mine to operate, and there is no built-in hybrid search.

PostgreSQL in production, SQLite locally

The same models and queries work in both, so a new checkout runs with one command.

Tradeoff A few dialect edges to watch, and local behavior is not a perfect stand-in for production.

Celery with an eager mode

Notifications run asynchronously in production and synchronously in development.

Tradeoff Fast setup, but dev and prod differ in timing, so ordering bugs can hide until deploy.

Observability Structured JSON logs, Prometheus metrics, optional OpenTelemetry traces, bounded retries, and dead-letter handling. A failed draft or a dropped webhook should be visible, not silent.
05

Outcome

ReSOLVE is built. I don't have measurements from a live support queue, so I'm not going to quote a resolution rate or hours saved — there is no baseline behind those numbers yet.

What exists
  • The full intake → triage → draft → human decision path
  • A deterministic triage fallback when the model is unavailable
  • Grounded drafting with citations and a confidence score
  • A review interface, plus an audit trail on ticket events
What I can't claim

Resolution rate, time saved, deflection, or production traffic. Those need a deployment and a baseline, and I don't have measurements from one yet. The next section is the measurement plan I'd run first.

06

What I'd change next

  1. Label a ticket set Build a labeled sample and report triage precision and recall per intent class. An accuracy claim needs a denominator.
  2. Measure draft acceptance Track how often a human sends the draft unchanged, and where they edit. That is the number that decides whether drafting is worth it.
  3. Evaluate retrieval separately Measure recall@k over the knowledge base before touching prompts, so a bad answer is traceable to retrieval or to generation.
  4. Price the automation Log tokens, model latency, and queue time per ticket so the system has a cost per reply, not just a demo.
  5. Replay from the audit log Turn stored tickets into a regression harness, so prompt and retrieval changes can be compared against a fixed set instead of vibes.
